# ⚠ Highest-priority finding: the evaluation sets may not test what the paper claims they test

This is a **construct validity** problem, and it is a bigger threat to the submission than any of the
LLM-as-a-judge issues. It is worth fixing before adding any new judge.

## The claim

§5.1: *"our evaluation questions must require reasoning over multiple text segments … many publicly
available evaluation sets … are often short factoids or can be answered using a single localised piece of
information … The evaluation sets are built using the corpus to produce QA pairs that **frequently require
reasoning over information distributed across multiple chunks, pages, or documents**."*

The whole thesis of EmbGen is that it beats document-local baselines (Knowledge-Instruct, EntiGraph) because
it assembles generation contexts *across* document boundaries. If the evaluation does not require
cross-document integration, the central hypothesis is untested.

## What the published prompts actually do

**Pop-QA-Cities-20 (Appendix D.6.1, Figure 16).** The prompt mandates a mix of
**50% surface-level / 40% intermediate / 10% expert-level** questions. The surface templates are pure
single-fact lookup — `"What is [entity]'s [attribute]?"`, `"When did [event] occur?"`,
`"Where is [place] located?"`. The multi-reference instruction is *"For questions beyond surface level, use
at least 2 references from **different paragraphs of the context**"* — different paragraphs of **one**
context, not different documents. So by construction **at least half** of this eval set is exactly the
"short factoid answerable from a single localised piece of information" the paper says it is avoiding.

**Wikitext-10 (Appendix D.6.2, Figure 17).** This is a **paraphrasing** prompt, not a multi-hop generation
prompt: *"come up with alternate questions and answers … different wordings than the original while
maintaining the similar meaning"*. Its input format is `">doc: [document] || >q: … a: …"` — a **single**
document with its existing Q&A pairs. Nothing in it induces cross-document reasoning. "You can combine
multiple questions for that doc" is within-document composition at most.

**SQuAD-20.** No eval set was generated; the native SQuAD set is used. SQuAD is single-paragraph extractive
QA — by design the *opposite* of multi-hop. The Claude prompt in Appendix D.7 selects *articles* that
"support cross-article reasoning", but the questions themselves are still stock SQuAD.

## Why this matters for the workshop submission

1. **The headline result is on Wikitext-10**, whose eval set is generated by a paraphrase prompt. A reviewer
   who reads Appendix D.6.2 will conclude the paper's best result is measured on reworded single-document
   questions — undercutting the cross-document story entirely.
2. It plausibly explains the **floor effect** (Binary Accuracy ≈ 0.07 on Wikitext-10, i.e. 93% of answers
   judged wrong). Paraphrased reference answers with a strict "all checkable claims must be entailed by the
   reference" rubric produce near-zero scores for reasons that have nothing to do with the training data.
3. No LLM-as-a-judge improvement can fix this. A better judge measures the same wrong construct more
   precisely.

**Caveat, stated honestly:** the appendix may not document the complete pipeline — there may be filtering,
selection, or a multi-document assembly step applied after generation that is not written up. **Verify
against the actual generation code before acting on this.** If such a step exists, the fix is to document
it; if it does not, the fix is below.

## What to do

**Cheap and decisive — a hop-count audit (no new annotation).** For each of the 250 eval items, record the
minimum number of distinct source chunks/documents whose content is needed to produce the reference answer.
You already have `<REFERENCE> LINE:#` provenance for the Pop-QA set — that is the audit, already collected.
Report the distribution. Then **stratify every result table by hop count** (1-hop vs ≥2-hop). If EmbGen's
advantage concentrates in the ≥2-hop stratum, that is a far stronger and more mechanistic result than the
current aggregate number, and it *directly* evidences the paper's thesis.

**A single-document oracle control.** Feed each question to the un-finetuned Llama-3-8B-Instruct together
with (a) only the single best-matching chunk, then (b) the full set of relevant chunks. Questions answerable
from (a) are not multi-hop. This is the standard sanity check for multi-hop benchmarks and is cheap — it is
inference only, no training.

**An external, human-authored multi-hop control set.** Add a small slice of MuSiQue, 2WikiMultiHopQA or
FanOutQA over the same corpora where feasible. Human-written multi-hop questions remove the circularity of
"we generated the training data and the test data with LLMs."

**If the hop-count audit comes back mostly 1-hop:** regenerate the eval sets with a prompt that *requires*
evidence from ≥2 distinct source documents and records the provenance, then rerun. This is the single
highest-value experiment available for this submission — higher than any judge refinement.
